what this number is not

Six ways to get a higher number, and why we took none of them.

The gap between a real autonomous result and a dressed-up one is small on the leaderboard and large in the logs. Before the run is replayed below, here is what it was not allowed to do. Every line is checkable in the repo.

No seeded solution

The run starts from the published FM baseline, reproduced on three seeds. No champion script, checkpoint, or tuned configuration is handed to it as a starting point.

No recipe in the prompt

Method cards say what a technique is, when it applies, and what it measured. They never carry a config to copy. With cross-run memory switched off the same loop reached 0.6051; with every measured number removed from the cards (literature only) it still found the same opener and reached 0.6033.

No contact with the hidden test set

Test data is never copied into the agent's workspace. Nothing was tuned, selected, or stopped on a test score. The final model was trained on train only and applied to test exactly once, for the CSV.

The stopping rule is the competition's, applied literally

Three iterations without a 0.002 gain end the run. The run stopped at six. No override, no continue-past-convergence flag, no rule rewritten until a run survived.

reset the counter on every accept, or keep going → converged, not peak

No hand-picked run

All 146 runs are in the ledger with their scores, including the ones that lost. The designated run is the best converged clean run by the rule, not the best of many with the rest deleted.

the machine

Diagnose, treat, retrain, measure. Repeat until the stopping rule fires.

No human picks the next move. The agent reads its own training curves, chooses a treatment from a library of cited method cards, edits the model code, retrains, and keeps a change only if the gain is bigger than measurement noise (the acceptance gate). The run ends by the competition's stopping rule: three iterations in a row that fail to beat the best score by 0.002 (epsilon). A rule, not a person, ends the run.

the model it ended with

Six mechanisms, chosen one iteration at a time.

This is the model behind 0.6056, read straight from the accepted nodes' journals and metrics. Each piece is a published technique from the card library; the agent picked it against a diagnosis, and the dials were found by its own search, not written down for it.

01 · DCN-lite instead of plain FM

The baseline is a factorization machine (FM): every field gets a 16-dimensional embedding, and pairwise dot products score the impression. DCN-lite keeps that and adds one cross layer plus a small MLP (128 → 64 → 1), so the model can learn feature interactions beyond pairs at almost no extra cost. Same five official fields, same k = 16 (measured optimal on Pure).

iteration 3 · diagnosis: overfit at epoch 8 · chosen as the base of the "package"

02 · A pairwise (BPR) term next to the pointwise loss

The metric ranks each user's own videos, but binary cross-entropy (BCE) trains on absolute probabilities. The loss becomes 0.5 · BCE + 0.5 · BPR: for pairs of one positive and one negative impression from the same user, penalise the negative scoring higher. This aligns training with the per-user ranking the evaluator measures.

iteration 3 · from the bpr-hybrid card · the mix, 0.5, came from the in-node search

03 · Recency weighting

Validation is the week after training. Each training row is weighted by 2−age / half-life with a 7-day half-life, so the model leans towards recent behaviour and the temporal drift the diagnosis kept pointing at. Tried alone in iteration 2 it did nothing (+0.0000); inside the package it was kept because the sweep measured it as a component that helped.

iteration 2 alone: rejected · iteration 3 in combination: kept, half-life 7 days

04 · Strong regularization plus rapid learning-rate decay

The overfit diagnosis is answered directly: dropout on the embeddings, AdamW weight decay, and a step schedule that multiplies the learning rate by 0.57 every two epochs, so the model settles before it starts memorising. The exact dials (dropout 0.18, weight decay 9e-5, decay ×0.57) are not from any card. The node ran its own two-stage random search, 8 coarse then 6 refining probes, and picked them.

iteration 3 · package-dial-sweep card · 0.6018 → 0.6042, accepted at +0.0024

05 · An auxiliary watch-time objective, tried and rejected

Iteration 5 added an ordinal watch-ratio head on top of the accepted model, hoping duration structure would help ranking. It scored 0.6030, below the incumbent, and the harness threw it away. It is in the recipe as a negative: the final model uses nothing but the long_view label.

iteration 5 · rejected, journaled · iteration 4 was a failed proposal (VOID)

06 · A seed ensemble, designed by the agent

With the single model settled, remaining variance is seed noise. The closing node retrained the accepted recipe with seven different seeds, then chose on validation how many to keep (3, 5 or 7) and how to combine them (averaged probabilities versus per-user rank average). It picked three members, seeds 42-44, rank-averaged within each user.

iteration 6 · seed-ensemble card · 0.6042 → 0.6056, accepted at +0.0013 · then three flat iterations ended the run

The test CSV was rebuilt from this recipe by tools/predict_test_bc07.py: the same three members retrained on train only, applied to test once. Four other runs with no cross-run memory found the same shape (DCN-lite, BPR hybrid, recency, strong regularization, seed close) at 0.6045-0.6052, which is the sense in which the campaign converged on a technique rather than a number.

how it worked

The four stages, in depth.

You just watched six iterations. Here is exactly what happened inside each stage of every one of them.

01 · DIAGNOSE

Every trained model logs a learning curve: training loss and validation score at every epoch. The agent reads that curve the way an engineer would. Validation peaking early and then sliding while training loss keeps falling means overfitting. Both still improving at the last epoch means undertraining. A flat curve on a changed model means the idea did nothing. And because the run measures the baseline's run-to-run randomness first (3 seeds, σ ≈ 0.0001), the agent can tell a real effect from a lucky run by reading the gain as a multiple of that noise (sigmas). A telemetry gate keeps it honest: a diagnosis may only cite a curve that was actually recorded, and every diagnosis is written verbatim into the journal, so wrong calls stay visible. The one you just saw replayed, "validation peaks at epoch 8", is what steered the whole run.

02 · TREAT

The diagnosis selects from a library of 42 method cards, each a real technique from the ranking literature written down with its mechanism, when it applies, and what it has measured on this dataset so far. Overfitting points at regularization cards; a plateau points at combining models or switching to a different model type (a family switch). The menu has two tiers, proven fixes versus promising but untested ones, and a strategy layer keeps the run phase-appropriate: establish a strong base first, build on what measured, close by blending different model types (a cross-family ensemble).

03 · RETRAIN

The agent then writes a complete training script implementing the chosen treatment, against a frozen contract: read the prepared splits, train, emit validation predictions plus the per-epoch history the next diagnosis will need. A 360-second trial run (smoke test) catches crashes before the full train. The hidden test set, the data the final submission is scored on, is never copied into the workspace, so leakage is impossible by construction rather than by instruction. If a script crashes, a fixer model gets one repair attempt; an unrecoverable crash is logged VOID and the loop moves on.

04 · MEASURE

The official evaluator scores how well the model ranks each user's own videos (validation GAUC and nDCG@5 per user; the primary metric is their mean). A change is kept only if it clears an acceptance gate set against measured noise: in the designated run gains under a 0.0009 floor (well above 2σ) did not count on their own, and borderline gains had to repeat on a fresh seed with the mean still clearing 0.001 (iteration 1 failed exactly that check); later harness versions lowered the floor to 0.0005 and added a z-test. The winning close of bigclock_07 was accepted at +0.0013. The stop is the competition's rule (epsilon): the run ends when three iterations in a row fail to beat the best by 0.002, hard cap 50. The run you just scrolled through ended exactly that way, with no human in the decision.

the system

One loop, two halves: the agent proposes, the harness checks and scores.

The LLM lives in the top lane: it reads the recorded training curves, picks a cited method card, and writes a training script. Everything below the line is fixed code with no LLM in it (the harness): screening, a trial run, training on the fixed split, official scoring, and a gate that rejects gains smaller than measurement noise. The hidden test set has no path into the loop at all.

  • 01 · TOP LANEThe agent proposes. Reads the last curves, names the bottleneck, picks a card, writes the whole training script.
  • 02 · BOTTOM LANEThe harness executes and scores. Screens the code, smoke-tests it, trains on the fixed split, scores with the official evaluator, keeps the change only if the gain beats measured noise.
  • 03 · THE RETURNEverything is journaled. Accept or dead end, the verdict goes back into the run's memory, so later iterations do not relearn it.
  • 04 · THE EDGESA rule ends it; the test set never enters. Three iterations in a row without a 0.002 gain (the epsilon rule) stop the run. The hidden test set is never copied into the workspace, so no path to it exists.

Structural leakage guard

The rule "never touch the hidden test set" (the data the final submission is scored on) is enforced by architecture, not by prompt. A data exporter builds the agent's workspace containing only the train and validation windows; the test file simply does not exist in any path the agent's scripts can read. On top of that, every generated script is screened before execution for test-window access patterns, and the two test-prediction tools (tools/predict_test*.py) carry explicit guards and are never callable by the agent. The hidden test set was scored exactly once, at final submission. When organizers acknowledged the test set ships with the data and asked teams not to use it, this structural guard became a differentiator: our compliance is checkable from the code, not attested.

Calibrated acceptance gate

Iteration zero trains the official baseline on three random seeds and measures how much the score moves by chance alone: σ ≈ 0.0001 on the validation primary score. Every later gain is read in those units. A candidate is accepted outright only above a floor; borderline gains (the grey zone, floor 0.0005) must repeat on a fresh seed and pass a statistical test (a z-test) against that noise before they count. We measured why this matters: the competition's 0.002 stopping rule (epsilon) silently kills honest +0.0004 steps from a strong base, so a run that chases every twinkle converges early on noise, and a run with no floor accepts phantoms. The gate is versioned (floor-v2) and its history is in the repo, including the runs the earlier version handled worse.

The method-card library: 42 techniques, cited and measured

The agent's knowledge is not a prompt, it is a curated library compiled from the ranking literature (research/ surveys) and this campaign's own ledger. Each card names the mechanism, when it applies, its citation, and what it has measured on this exact dataset, updated as runs conclude. Cards move through honest states: measured-win, measured-dead (may not be re-selected in the same form), untried, parent-conditional. Telemetry-gated diagnosis, and the bug that taught us why

Every training script must emit its per-epoch history: train loss, validation GAUC, nDCG@5, learning rate. The diagnosis stage may only assert curve shapes that exist in that record; a proposal reasoning from an unrecorded curve is rejected as insufficient telemetry, and the run says so in its journal. We learned this the expensive way: mid-campaign we found two out-of-date knowledge sources (an outdated directive and 17 stale card statuses) had been silently mis-steering selection for a day of runs. We purged them, rebuilt the channel so knowledge is loaded once at launch, and disclosed the two runs the earlier wrong doctrine had discarded rather than deleting them. Accurate memory turned out to be as important to autonomous research as model quality.

The final ensemble: the agent plans, the harness executes

A seed close pays by how much variance the single left: +0.0013 off a 0.6042 single (bigclock_07), +0.0002 off a tuned 0.6051 single (f9); cross-family blends beat that only when every member is individually competitive, and closes built from fresh in-run members fell back to the incumbent every time. The farm-close move, a final ensemble of different model types, turns that into a first-class capability. The agent emits a structured, machine-checked plan (typed JSON): which model types, which configs and seeds, which blend rule. Fixed code (the assembler) then runs the three phases: quick low-cost fits of every model type in parallel (probes), every declared blend scored over those probe outputs (cheap: rank averages of saved arrays), full training of only the model types that complement each other, and a full re-verification of the winning combination before anything is emitted. There is no LLM call inside the measurement path, an anchor rule guarantees a strong singleton fallback, and a legitimate "the incumbent won" is recorded as such rather than punished as a degenerate ensemble.

Decision benches: testing judgment like code

How do you regression-test an agent's judgment? We froze real run states (curves, menu, history) whose right next move we knew from measurement, and replay the agent's decision-maker against them after every harness change. The full-knowledge selector bench runs 8/8; the clean-mode strategy bench went 4/10 to 10/10 through methodology fixes alone, under a standing constitution: a bench fix may only be an evidence correction or a general principle, never a canned answer to a specific state. A third tool replays historical decision points over cached artifacts; it scores 0.60599, which we report as an optimistic cached-artifact counterfactual, not a result, a distinction an external review pushed us to sharpen and that we adopted across every claim on this page.

design decisions

What we chose, and what it cost.

Six calls that shaped the system. Each one had a cheaper alternative; each alternative was rejected for a measured or structural reason.

Designate only clean runs

The submitted run starts from the published baseline with no seed scripts. Seeded combinations exist in the ledger, but only as experiments.

seed the run with our best code → provenance over score: the exhibit must prove the agent, not us

Method cards, not a mega-prompt

Knowledge is 42 versioned cards with citation, mechanism, preconditions, and measured evidence, updated as runs conclude.

ever-growing prompt of tips → auditable, correctable, honest states (measured-dead cards cannot be re-picked)

Medium reasoning effort

In the designated run the proposing LLM ran at medium reasoning effort. High and extra-high were measured at the time: proposals truncate or fail (runs 16-22, 27, 28 in the ledger).

max effort everywhere → measured reliability beats theoretical depth

Accept only gains bigger than noise (floor-v2)

Baseline run-to-run noise is measured first (3 seeds, σ ≈ 0.0001). Gains are read as multiples of it (sigmas); borderline gains must repeat on a fresh seed and pass a z-test.

accept any positive delta → phantom gains rejected; the 0.002 rule alone kills honest +0.0004 steps

For the final ensemble the agent writes a structured, machine-checked plan; fixed code runs the trial fits, the blends, and the re-verification.

let the LLM run the measurement → no LLM in the measurement path, ever
