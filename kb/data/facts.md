# Data facts — what the EDA means

Read this first; go to `eda_report.md` (generated by `eda.py`) only when you need the exact number.
Label diagnostics: `label_check.py`. Everything here is measured on train + valid; the only test-label numbers are
the organizers' published composition, reproduced as a harness check.

## 1. The catalogue is closed — there is no item cold start
Every video and every author in valid and test also appears in train (0.0 % unseen). Only 3.6 % of test rows come
from users unseen in train. So `user_id`, `video_id`, `author_id` embeddings are fully informed at test time, and
static content features (music, type, tags) can only add what a video's own embedding does not already carry —
which is why the organizers' "+13 fields" ablation was flat. Item-side generalisation is not the problem; ordering
within a user is.

## 2. Users have tens of interactions, not hundreds
Valid users have a median of 35 train rows (p10 = 6, p90 = 103, max 809). The README's "hundreds to thousands" is
an overstatement for Pure. Sequence models (DIN / SIM) would work with short histories; simple per-user history
aggregates (rates by author, tab, duration bucket) may capture most of what a sequence model would.

## 3. The label is duration-defined, and short videos are the HARD case
`long_view = play_time_ms >= min(duration_ms, 18 000)` holds exactly, with two documented exceptions:
- rows with `duration_ms = 0` (unknown duration; 1.9 % of rows; the video has no entry in the features file) are
  **always labelled 0**;
- 0.24 % of short-video rows are labelled 1 with play time just under the duration (a completion tolerance).

Positive rate by duration bucket: **0.28 for ≤ 11.6 s, 0.27 for 11.6–19.6 s**, rising to 0.38 around 90–117 s, then
0.32 for the longest videos. A short video must be *completed*; a long one needs only 18 s. (Prior overturned: the
guess that short videos are easier to long-view was wrong.)

Implications: (a) an explicit `duration_unknown` flag separates always-negative rows from genuinely short videos —
the baseline's `dur_bucket 0` mixes them; (b) predicting watch time targets the mechanism that generates the label;
17.2 % of rows are completed plays, i.e. censored watch time (the CWM paper's point).

## 4. `tab` is a huge signal — already in the baseline
tab 1 = 73 % of rows (positive rate 0.39); tab 0 = 13 % (**0.04**); tab 4 = 7 % (0.49); tab 6 = 3 % (0.09). A
user's impressions across tabs are ranked together, so tab alone separates a lot. New features must add value
beyond tab × item.

## 5. Volume and positive rate drift over time
Rows per day: 04-10 / 04-11 ≈ 230–280 K, falling to ≈ 20 K/day by 04-18 and staying there through valid
(14–27 K) and test (13–21 K). Positive rate: 0.31–0.38 across train (peak 04-15/16), 0.29–0.34 in valid, falling
through the valid week. The last four train days resemble valid/test; the early days dominate training by volume.
→ Recency weighting / time-aware training is a live lever, and FM's valid→test drop (−0.007) is drift, not noise.
No rows exist for 2022-04-08; train effectively spans 04-09 → 04-21.

## 6. Other feedback signals: one strong helper, five sparse ones
`is_click` (= a valid play ≥ 7 s in this UI) correlates 0.76 with long_view; P(long_view | click) = 0.72,
P(click | long_view) = 0.996 — a coarser version of the same label, a natural auxiliary target. like (1.9 %),
follow (0.1 %), comment (0.3 %), forward (0.1 %), hate (0.04 %) are too rare to carry much on their own.

## 7. Cohort structure: valid is composed differently from test
Valid: 30.3 % all-negative users (nDCG ≡ 0), 11.9 % all-positive, 57.8 % discriminative; oracle primary 0.8484.
Test (published, reproduced exactly): 27.1 / 9.2 / 63.7; oracle 0.8645. Valid users average 5.6 impressions
(median 4), test 7.2 (median 5). Compare models against each other on valid; never read valid numbers on the test
scale.

## 8. Evaluation-set quirks
- `(user, video)` pairs repeat: 6.1 % of test rows sit in a repeated pair (max 12×), 5.7 % in valid. (The
  organizers' 3.06 % counts the extra copies.) Repeats can carry different labels; a model that scores identical
  inputs identically pays for that. `row_id` is the key.
- Users span all splits: 27,285 in the features file; 26,210 / 22,377 / 23,875 in train / valid / test.
- Hour of day: positive rate 0.32–0.38, morning highest. Weak.
- `is_rand` = 0 throughout the standard log. The 1.19 M random-exposure rows are a separate file overlapping
  valid + test dates — an unbiased-validation lever; using them for training is a rules question.

## 9. What this suggests about where to spend iterations (priors — to be tested, not conclusions)
1. Loss aligned with the metric (pairwise / listwise) — untouched by any finding above; still lead #1.
2. `duration_unknown` flag and finer duration handling — cheap, mechanism-backed (§3).
3. Recency weighting / emphasis on the last train days — mechanism-backed (§5).
4. `is_click` as an auxiliary target — strong and cheap (§6).
5. Watch-time modelling — mechanism-backed, heavier (§3).
6. Sequence models — histories are short (§2); try history aggregates first.
7. Static content features — expect nothing (§1) unless a different model family consumes them differently.
8. Exposure-sequence features — label-free, tab-aware: same-author runs and repeat exposure (§10). Small share of
   rows; large within-tab effects where they apply.

## 10. User behaviour around exposures (measured on `workspace/data/train.csv` by the review session, 2026-08-30;
base P(long_view) = 0.337; reproduced by `eda.py` — exact table in `eda_report.md` § "User behaviour around exposures")
1. **Series continuation is real but label-conditioned.** If the user's previous impression was by the same author
   AND was long-viewed, P(long_view) = 0.78 (2.3×); if it was NOT long-viewed, 0.077. In tab 6, given the previous
   same-author impression was long-viewed, 1.000 (n = 1,195). The previous impression's LABEL is unobservable in the
   valid/test windows (no outcome columns), so this is usable only through train history (≥ 1 day stale) or through
   label-free proxies (fact 2).
2. **Label-free same-author-consecutive exposure is a NEGATIVE signal.** P(long_view) = 0.142 overall when the
   previous impression (any label) was by the same author. It is concentrated in profile/series tabs (share of rows
   that are same-author-consecutive: tab 5 46 %, tab 6 47 %, tab 1 0.6 %), so much of it is
   tab, which the FM already has — but WITHIN tab 1 it is still 0.268 vs 0.384 and within tab 4 0.393 vs 0.489.
   Occurs in 2.7 % of valid rows. Observable proxies: the run length of consecutive same-author exposures so far and
   the position in the run (a 10-run is profile browsing, a 2-run a series). Legal: computed from features
   (author via video, time_ms) of strictly earlier rows, including earlier valid rows, never from labels.
3. **Creator affinity is real but almost unavailable in Pure.** User × author prior long-view rate ≥ 0.5 → 0.42 vs
   < 0.2 → 0.14; but 96.6 % of valid rows are authors the user NEVER saw in train and only 0.1 % have ≥ 3 prior
   exposures — which is why `history-user-aggregates` measured flat on the BPR stack. "New creator" (no prior
   exposure) ≈ base rate 0.343; a re-exposed author 0.247 (label-free, negative).
4. **Same-video repeat exposure is label-free and negative:** in tab 1, 0.283 vs 0.384 (n = 22 K; 0.216 vs 0.342 over all tabs); 5.7 % of valid
   rows are repeated (user, video) pairs (§8). live_04 node_005 (exposure count 0/1/2/3+ and log time-since) scored
   −0.0005 on one seed, unconfirmed — a candidate for a cleaner retest (within-window exposure sequence, tab-aware)
   rather than a dead lever.
5. **Session position and density are the strongest label-free signals measured** (tab 1 only, train; base 0.337):
   P(long_view) by position in the session (a gap > 30 min starts a new one) 1st 0.418 · 2nd–3rd 0.387 · 4th–10th 0.333 ·
   11th–30th 0.243 · beyond 0.137; by impressions in the previous 10 min 0 → 0.413 · 1–3 → 0.350 · 4–10 → 0.207 ·
   > 10 → 0.120; by gap since the previous impression < 0.5 min 0.361 · 10–60 min 0.399 · > 60 min 0.417. Attention
   budget per impression is the mechanism; the features vary within a user's list and need only `time_ms` of earlier
   rows (card `features-exposure-session`).
